------------------------------------------------------------------------------------------
 1. O QUE É O COILLECT
------------------------------------------------------------------------------------------

Coleta de óleo de cozinha usado em condomínios. Cada condomínio tem um BARRIL com um SENSOR
ultrassônico (ESP32 + HC-SR04) que mede o nível. Quando o barril passa do limite (80%), a API
cria uma SOLICITAÇÃO DE COLETA daquele barril específico para a EMPRESA COLETORA. O SÍNDICO só
é NOTIFICADO (cópia informativa; ele não controla a coleta). Um ADMINISTRADOR cadastra e acompanha
tudo pelo app desktop.

Objetivo: MVP demonstrável em aula. Nada de produção, sem clientes reais.

Peças:
  - Sensor: ESP32 físico, ESP32 virtual no Wokwi (simulador online) ou sensor virtual no PC.
    Todos mandam o MESMO pedido HTTP: POST /api/sensor-alert {sensorId, percentual, dataHora}.
  - API (NestJS + PostgreSQL) com o "listener" que decide abrir a solicitação.
  - Azure Storage: Queue (fila que entrega os avisos) e Blob (comprovante de cada coleta).
  - 3 apps: app do síndico (Android), app da empresa (Android), administração (desktop).

 4. COMO O SISTEMA FUNCIONA
------------------------------------------------------------------------------------------

4.1 Fluxo ponta a ponta

  Sensor (ESP32 / Wokwi / simulador / "Simular leitura" do app do síndico)
    │  POST /api/sensor-alert {"sensorId":"CLT-8472-A","percentual":86,"dataHora":"..."}
    ▼
  API: grava a leitura, atualiza o nível do sensor
    │  LISTENER: barril ≥ limite? já tem coleta aberta? empresa vinculada?
    ▼
  Cria UMA solicitação de coleta (PENDING) do barril  ──► resposta ao sensor (na hora)
    │
    │  publica mensagem na FILA "coillect-notificacoes" (Azure Queue Storage)
    ▼
  Consumidor da fila (dentro da API, lê a cada 1–5 s)
    ├─► EMPRESA: aviso "Nova solicitação de coleta" (faixa laranja no app)
    └─► SÍNDICO: cópia informativa ("Coleta solicitada automaticamente")

  Empresa no app: "Agendar coleta" (SCHEDULED) → síndico avisado ("Coleta agendada")
  Empresa no app: "Concluir coleta" (COMPLETED) → barril volta a 0%
    └─► pela fila: síndico avisado + COMPROVANTE JSON gravado no Azure Blob Storage
        (container "comprovantes-coleta"), visível no Histórico dos dois apps
  Síndico: "Precisa de ajuda?" → pela fila → aviso "Pedido de ajuda" no app da empresa
  Desktop: acompanha tudo, mostra as leituras ao vivo, cadastra, reinicia a demonstração e
           mostra a fila e o Blob (aba "Nuvem (Azure)", com Pausar/Retomar o consumidor).

4.2 Regras de negócio (todas testadas no CI)

  - Limite padrão: 80% (configurável por barril). Abaixo do limite: nada acontece.
  - No máximo UMA solicitação aberta (PENDING ou SCHEDULED) por barril: leituras repetidas não
    duplicam (motivo REQUEST_ALREADY_OPEN).
  - Depois de uma coleta concluída, o barril só abre nova solicitação quando o sensor ler um nível
    ABAIXO do limite (motivo AWAITING_EMPTY_READING). Motivo: no Wokwi, o barril simulado continua
    "cheio" até alguém arrastar o controle.
  - Sem empresa vinculada ao condomínio: não cria (NO_COMPANY_LINKED). Sensor sem barril:
    SENSOR_NOT_INSTALLED.
  - O síndico NÃO cancela nem conclui coletas do sensor ou da empresa (HTTP 403).
  - A empresa pode "Agendar coleta" mesmo antes do alerta (cria solicitação de origem COMPANY).
  - Notificações são idempotentes (mensagem repetida da fila não duplica aviso).

4.3 Modo Azure x modo local (a API funciona nos dois)

  - Com a variável AZURE_STORAGE_CONNECTION_STRING: fila e comprovantes no Azure Storage.
    "UseDevelopmentStorage=true" = Azurite, o emulador oficial (sem conta na Azure).
  - Sem a variável: modo local (comprovantes na pasta backend/storage-local, fila em memória;
    os avisos saem na hora). Útil para desenvolver sem Docker.
  - O docker-compose.yaml já sobe o Azurite e liga a API nele: localmente você vê o mesmo
    comportamento da nuvem.
  - GET /api/health mostra "storage": "azure" ou "local".

5.4 Sensor — escolha uma opção

       node sensor-esp32/simulador-pc/sensor-virtual.mjs --api http://localhost:3000/api
     Painel em http://localhost:4010 (encher/esvaziar o barril, enviar leitura, simular alerta).
     Vários sensores: --sensores CLT-8472-A,CLT-1264-B,CLT-9801-C
  b) ESP32 virtual no Wokwi (wokwi.com): o Wi-Fi "Wokwi-GUEST" só enxerga a internet, não o
     "localhost" do PC. Opções: usar a URL da API na Azure (seção 8) ou abrir um túnel:
       cloudflared tunnel --url http://localhost:3000
     e usar https://<endereço>.trycloudflare.com/api/sensor-alert em COILLECT_API_URL no começo
     de sensor-esp32/coillect_sensor/coillect_sensor.ino. Cole o .ino e o diagram.json num
     projeto ESP32 novo no Wokwi e clique ▶. Arraste a distância do HC-SR04 (distância menor =
     barril mais cheio; tabela em sensor-esp32/README.md). LED verde = API OK; LED vermelho =
     alerta; botão azul = enviar agora.
  c) No app do síndico: "Simular leitura do sensor" (− / + e bolinhas de 20%).
  d) Uma leitura avulsa (Git Bash/Linux/macOS):
       curl -X POST http://localhost:3000/api/sensor-alert -H "Content-Type: application/json" \
            -d '{"sensorId":"CLT-8472-A","percentual":86}'
     No PowerShell use Invoke-RestMethod, ou simplesmente o Swagger (/api/docs → Try it out).

5.5.1 Celulares de verdade (síndico e empresa ao mesmo tempo)
  Como funciona: os apps NÃO falam entre si. Cada celular (e o desktop, o sensor e o simulador)
  conversa com a MESMA API pelo endereço digitado em "Servidor da API"; os apps atualizam a tela
  a cada 5 s. A API é a única fonte da verdade: o que a empresa faz aparece no celular do síndico
  na próxima atualização, e vice-versa.
  a) Instalar o APK no celular (uma vez por app):
     - GitHub → repositório do app → Releases → "demo" → coillect-sindico.apk ou
       coillect-empresa.apk (o CI atualiza a cada merge na main; os repositórios são privados:
       entre no GitHub no celular ou baixe no PC e passe o arquivo). Permita "instalar apps
       desta fonte".
     - Ou Android Studio com o celular no cabo USB (Opções do desenvolvedor → Depuração USB)
       → ▶ Run.
     - O APK usa uma chave de debug fixa: versões novas instalam por cima (sem desinstalar).
  b) Escolher onde a API roda (todos os clientes usam o MESMO endereço):
     - PC na mesma Wi-Fi dos celulares. No PC (pasta CoillectApp), com a API no ar:
         node backend/scripts/endereco-celular.mjs
       Ele mostra o IP certo (ignora adaptadores do WSL/Docker) e o comando do firewall do
       Windows (PowerShell como administrador, uma vez):
         New-NetFirewallRule -DisplayName "Coillect API 3000" -Direction Inbound -Protocol TCP
           -LocalPort 3000 -Action Allow -Profile Any        (tudo numa linha)
     - Wi-Fi que isola aparelhos (comum em faculdade): hotspot de um celular para o PC e os
       outros celulares, ou túnel público: cloudflared tunnel --url http://localhost:3000
     - Nuvem: a URL do App Service (seção 8). É a opção mais simples para a aula: funciona em
       qualquer rede, inclusive 4G, e o Wokwi usa o mesmo endereço.
  c) No app: digite só o IP ou o domínio (ex.: 192.168.0.15 ou app-coillect.azurewebsites.net);
     o app completa http(s)://, a porta 3000 (para IP) e o /api. Toque em "Testar conexão":
     ele chama GET /api/health e diz se achou a API ou o que conferir (mesma rede, firewall,
     endereço). Depois "Entrar". O app lembra o servidor e o e-mail; o menu lateral mostra o
     servidor em uso.
  d) Mais de um cliente ao mesmo tempo é seguro: leituras simultâneas do mesmo barril (Wokwi,
     simulador, "Simular leitura") e "Agendar coleta" chegando juntos abrem UMA solicitação só
     (a API processa um barril por vez; há teste e2e para isso). Na apresentação, use UMA fonte
     de leitura por sensor para o nível não "pular" entre valores diferentes.

5.9 Problemas comuns
  - "port is already allocated": algo já usa a porta 3000/5482/10000; feche ou troque a porta.
  - API não sobe: docker compose logs backend; o banco pode demorar alguns segundos (a API
    tenta reconectar sozinha).
  - App não conecta: use "Testar conexão" na tela de login. No emulador use 10.0.2.2; no
    celular, o IP mostrado por node backend/scripts/endereco-celular.mjs + firewall liberado
    (ou túnel / Azure, seção 5.5.1).
  - Wokwi não chega na API: localhost não funciona lá; use túnel (5.4 b) ou a URL da Azure.

     coillect-notificacoes mostra a mensagem → "Retomar consumidor" → o aviso chega em segundos.
 10. (A02, monitoramento) Dashboard "Coillect — Operação" no portal: nível dos barris, coletas,
     fila, comprovantes, saúde da API (docs/azure-a02.md §4).
 11. Se perguntarem: depois da coleta, o mesmo barril só reabre solicitação quando o sensor ler
     o barril vazio (AWAITING_EMPTY_READING) — evita coleta duplicada.

8.2 Opção A — Azure (recomendada para a A02)
  Siga docs/azure-a02.md §7. Resumo:
   0. GitHub → Packages → coillect-api → Package settings → Change visibility → Public
      (uma vez; sem isso o App Service não consegue baixar a imagem).
   1. Grupo de recursos rg-coillect (Brazil South; se a assinatura bloquear, East US).
   2. Storage Account → copiar a "Cadeia de conexão" (segredo!). Ativar soft delete e versões.
   3. PostgreSQL Flexible Server B1ms (acesso público + "permitir serviços do Azure").
   4. App Service (Contêiner, Linux, B1) com a imagem ghcr.io/coillectadm/coillect-api:latest.
      Variáveis: WEBSITES_PORT=3000, PORT=3000, DATABASE_URL, DATABASE_SSL=true, JWT_SECRET,
      SEED_DEMO=true, AZURE_STORAGE_CONNECTION_STRING. Always On ligado. Health check /api/health.
   5. Log Analytics + Configurações de diagnóstico do App Service + Application Insights (teste
      de disponibilidade de /api/health) + consultas KQL fixadas no Dashboard.
   6. Testar: node backend/scripts/smoke-flow.mjs https://<app>.azurewebsites.net/api --reset
  Assinatura: Azure for Students (US$ 100 de crédito por 12 meses, sem cartão). Custos: o
  App Service B1 é o principal (por volta de US$ 13/mês, varia com a região; confira na
  calculadora de preços da Azure); o PostgreSQL B1ms entra na oferta gratuita de 12 meses; o
  Storage custa centavos. Depois da avaliação, apague o grupo de recursos para parar a cobrança.

8.3 Opção B — Render (gratuito, alternativa)
  Render → New → Blueprint → repositório CoillectApp (usa render.yaml: API + PostgreSQL grátis).
  Para usar o Azure Storage mesmo assim: cadastrar AZURE_STORAGE_CONNECTION_STRING em Environment.
  Limites: a API "dorme" após 15 min (≈1 min para acordar; os apps esperam até 60 s) e o
  PostgreSQL gratuito expira em 30 dias. Detalhes em docs/deploy-cloud.md.

8.4 Depois do deploy, apontar todo mundo para a URL pública
  Apps e desktop: campo "Servidor da API" = https://<app>.azurewebsites.net/api/
  Firmware/Wokwi: COILLECT_API_URL = https://<app>.azurewebsites.net/api/sensor-alert
  Sensor virtual: --api https://<app>.azurewebsites.net/api

8.5 Publicar uma versão nova da API
  Merge na main → workflow "Imagem da API (GitHub Container Registry)" publica :latest → no
  App Service, "Reiniciar": ao reiniciar ele baixa a imagem de novo (confira em Fluxo de log).

 11. GLOSSÁRIO RÁPIDO
------------------------------------------------------------------------------------------

  Listener ............ trecho da API que "escuta" cada leitura e decide abrir a solicitação.
  Fila (Queue) ........ lista de mensagens: quem publica não espera quem processa.
  Consumidor .......... quem lê a fila; aqui, um laço dentro da própria API.
  Poison queue ........ fila para mensagens que falharam várias vezes (para análise).
  Idempotência ........ processar a mesma mensagem duas vezes dá o mesmo resultado.
  Blob ................ arquivo guardado no Azure Storage (aqui: o comprovante JSON).
  Container ........... "pasta" de blobs (aqui: comprovantes-coleta).
  Azurite ............. emulador oficial do Azure Storage, roda no PC/Docker sem conta.
  Connection string ... texto com o nome e a chave da Storage Account (é segredo).
  App Service ......... serviço da Azure que roda a API (aqui, a partir de um contêiner).
  GHCR ................ GitHub Container Registry, onde fica a imagem Docker da API.
  Health check ........ /api/health: a plataforma usa para saber se a API está saudável.
  KQL ................. linguagem das consultas do Log Analytics (gráficos do dashboard).
  PITR ................ restauração do banco para um ponto no tempo.
  Wokwi ............... simulador online de ESP32 (o "ESP32 virtual").
